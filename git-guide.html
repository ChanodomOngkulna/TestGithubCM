ภาพรวมก่อนเริ่ม: Git เก็บอะไร และเก็บที่ไหน

Git เก็บ "ภาพถ่าย (snapshot) ของโปรเจกต์" เป็นช่วงๆ แต่ละภาพเรียกว่า commit และแต่ละ commit รู้ว่าตัวเองต่อจาก commit ไหน ไฟล์ของคุณเดินทางผ่าน 4 ที่:

  • Working dir คือไฟล์ที่คุณเปิดแก้อยู่ในเครื่อง
  • Staging คือที่พักของที่เลือกไว้ว่า "รอบนี้จะเก็บอันนี้"
  • Local repo คือประวัติในเครื่องคุณ
  • GitHub (remote) คือประวัติกลางที่ทั้งทีมใช้ร่วมกัน

ตลอดคู่มือนี้ ใช้ทีมสมมติ 4 คน และ commit 5 อัน:

commitใครทำอะไร
aนาย กสร้างโปรเจกต์ (README.md บรรทัดแรกคือ # Shop)
b, cนาย ขทำหน้า login (2 commit)
dนาย คแก้ชื่อใน README เป็น # Shop Online
eนาย งแก้ชื่อใน README เป็น # Shop Mall

1. คำสั่งพื้นฐาน

คำสั่งทำอะไร
git clone <url>ดาวน์โหลด repo จาก GitHub มาทั้งประวัติ
git initสร้าง repo ใหม่ในเครื่อง (ถ้า clone แล้วไม่ต้องใช้)
git statusดูว่าไฟล์ไหนแก้แล้ว / add แล้ว / ยังไม่ติดตาม
git diffดูว่าแก้อะไรไปบ้าง (ที่ยังไม่ add)
git add <ไฟล์>เลือกไฟล์เข้า Staging (git add . = เลือกทุกไฟล์ที่เปลี่ยน)
git commit -m "ข้อความ"บันทึก snapshot จากของใน Staging
git log --onelineดูประวัติ commit แบบสั้น
git pushส่ง commit ในเครื่องขึ้น GitHub
git pullดึงของใหม่จาก GitHub แล้วรวมเข้ากับของเรา

ตัวอย่าง: นาย ก สร้าง commit a

git clone https://github.com/team/shop.git
cd shop
# สร้างไฟล์ README.md ที่มีบรรทัด  # Shop
git status                          # เห็น README.md เป็น untracked
git add README.md
git commit -m "a: เริ่มต้นโปรเจกต์"
git push

Branch และ HEAD ที่ต้องเข้าใจ

  • Branch คือ "ป้ายชื่อ" ที่ชี้ไปที่ commit หนึ่ง (ไม่ใช่การ copy โปรเจกต์)
  • HEAD คือ "ตำแหน่งที่คุณยืนอยู่ตอนนี้" ปกติชี้ไปที่ branch ที่คุณใช้อยู่

(ลูกศรจริงๆ ชี้ย้อนกลับไปหา commit ก่อนหน้า แต่วาดแบบนี้อ่านง่ายกว่า)

2. การทำงานเป็นทีม

หลักการคือ ไม่ทำงานบน main ตรงๆ ทุกคนแตก branch ของตัวเอง แล้วขอรวมผ่าน Pull Request (PR)

ทั้ง 3 คนแตกออกมาจาก a พร้อมกัน และทำงานขนานกันโดยไม่เหยียบกัน

นาย ข ทำ commit b, c

git switch main
git pull origin main                # ดึงของล่าสุดก่อนเริ่มทุกครั้ง
git switch -c feature-login         # สร้าง branch ใหม่แล้วย้ายไปอยู่
                                    # (ใช้ git checkout -b ก็ได้ผลเหมือนกัน)

# แก้ไฟล์ แล้ว
git add .
git commit -m "b: เพิ่มฟอร์ม login"
# แก้ต่อ แล้ว
git add .
git commit -m "c: เพิ่ม validation"

git push -u origin feature-login    # -u ครั้งแรกครั้งเดียว ผูก branch เครื่องเรากับ GitHub

จากนั้นไปที่ GitHub กด Compare & pull request (base: main ← compare: feature-login) แล้วให้เพื่อนรีวิว เมื่อ Approve แล้วกด Merge

หลัง merge แบบปกติของ GitHub (Create a merge commit) หน้าตาของ main จะเป็น:

ทุกคนที่เหลือต้องดึงของใหม่ลงเครื่อง

git switch main
git pull origin main

ถ้า main ขยับไปแล้วระหว่างที่คุณทำงาน

เช่น นาย ค ทำ d อยู่ แต่ main มี M แล้ว ให้เอา main มารวมใน branch ตัวเองก่อนส่ง PR:

git switch feature-title
git pull origin main        # = git fetch + git merge origin/main รวมกัน

ถ้าแก้คนละไฟล์หรือคนละบรรทัด Git รวมให้เองอัตโนมัติ แต่ถ้าแก้ บรรทัดเดียวกัน จะเกิด conflict ซึ่งคือหัวข้อต่อไป

3. การแก้ Conflict

Conflict คืออะไร: เกิดเมื่อสอง branch แก้ "จุดเดียวกัน" ของไฟล์เดียวกันจากฐานเดิมเดียวกัน แล้ว Git ไม่รู้ว่าจะเลือกอันไหน (Git ไม่มีทางรู้ว่าคุณอยากได้ Shop Online หรือ Shop Mall เลยหยุดแล้วให้คนตัดสิน)

สถานการณ์

ทั้ง ค และ ง แตกจาก a แล้วแก้บรรทัดแรกของ README.md

# Shop          ← ฐานเดิม (a)
# Shop Online   ← ค (d)
# Shop Mall     ← ง (e)

PR ของ ค ถูก merge เข้า main ก่อน ตอนนี้ main บรรทัดแรกเป็น # Shop Online พอ ง เอา main มารวม:

git switch feature-banner
git fetch origin
git merge origin/main

Git ตอบว่า:

CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

git status จะแสดง both modified: README.md ใต้หัวข้อ Unmerged paths และไฟล์จะถูก Git เขียนเครื่องหมายไว้ให้:

<<<<<<< HEAD
# Shop Mall
=======
# Shop Online
>>>>>>> origin/main

วิธีอ่าน:

  • ระหว่าง <<<<<<< HEAD กับ ======= คือ ฝั่งเรา (ของ ง ที่ branch ปัจจุบัน)
  • ระหว่าง ======= กับ >>>>>>> คือ ฝั่งที่เอามารวม (ของ ค จาก main)

ขั้นตอนแก้

ขั้นที่ 1: แก้ไฟล์ ตัดสินใจว่าจะเอาอะไร (เอาของใครคนเดียว หรือผสม เช่น # Shop Mall Online) แล้ว ลบบรรทัดเครื่องหมายทั้ง 3 แบบออกให้หมด ผลลัพธ์ต้องเหลือแค่:

# Shop Mall Online

(ถ้าใช้ VS Code จะมีปุ่ม Accept Current / Incoming / Both ให้กดแทนการลบเอง)

ขั้นที่ 2: บอก Git ว่าแก้เสร็จแล้ว

git add README.md
git commit              # Git เตรียมข้อความ merge ให้แล้ว กด save ได้เลย
git push

ขั้นที่ 3: PR บน GitHub จะอัปเดตเอง และข้อความ conflict หายไป

ถ้าตกใจ อยากยกเลิกกลับไปก่อนเริ่ม merge: git merge --abort

ข้อควรระวัง: ถ้าไม่แน่ใจว่าบรรทัดของอีกฝั่งสำคัญอย่างไร ให้ถามเจ้าของ commit นั้นก่อนตัดสินใจ อย่าเลือกเอาของตัวเองไว้ก่อนโดยไม่ดู

4. การย้อน Version

เพื่อความง่าย สมมติ main มี 5 commit ต่อกันเป็นเส้นตรง และพบว่า d (ของ ค) มี bug

คำถามแรกที่ต้องตอบก่อนเลือกคำสั่ง คือ ของที่จะย้อนนั้น push ขึ้น GitHub ไปแล้วหรือยัง

กรณี A: แค่อยากดูของเก่า (ไม่แก้ประวัติ)

git log --oneline                 # หา hash ของ commit ที่ต้องการ
git show b:README.md              # ดูไฟล์นี้ ณ commit b
git switch --detach b             # ย้ายไปอยู่ที่ b ทั้งโปรเจกต์ (detached HEAD)
git switch main                   # กลับมา

ตอน detached HEAD ให้ดูอย่างเดียว อย่า commit เพราะ commit จะไม่อยู่บน branch ไหน

กรณี B: ยังไม่ commit แล้วอยากทิ้งสิ่งที่แก้

git restore README.md             # ไฟล์กลับไปเหมือน commit ล่าสุด
git restore --staged README.md    # (ถ้า add ไปแล้ว) เอาออกจาก Staging ก่อน

ระวัง: คำสั่งนี้ทิ้งการแก้ไขถาวร เรียกคืนไม่ได้

กรณี C: push ไปแล้ว (คนอื่นอาจดึงไปใช้แล้ว) → ใช้ git revert

revert ไม่ลบประวัติ แต่ สร้าง commit ใหม่ที่ทำตรงข้าม กับของเดิม

git revert d
git push

ประวัติครบ ทุกคน git pull แล้วได้ผลเหมือนกัน นี่คือวิธีที่ปลอดภัยสำหรับ branch ที่แชร์กัน

ข้อควรรู้: ถ้า e แก้ทับจุดเดียวกับ d อาจเกิด conflict ตอน revert ให้แก้แบบหัวข้อ 3 และถ้า commit ที่จะ revert เป็น merge commit ต้องเติม -m 1 (เช่น git revert -m 1 <hash>)

กรณี D: commit ในเครื่อง ยังไม่ push → ใช้ git reset

reset คือ ย้ายป้าย branch ถอยกลับ สมมติ d, e ยังอยู่แค่ในเครื่อง:

มี 3 โหมด:

โหมดป้าย branchการเปลี่ยนแปลงของ d, e
--softถอยไป cยังอยู่ใน Staging พร้อม commit ใหม่ได้เลย
--mixed (ค่าเริ่มต้น)ถอยไป cยังอยู่ในไฟล์ แต่ไม่อยู่ใน Staging
--hardถอยไป cทิ้งทั้งหมด ไฟล์ในเครื่องกลับไปเหมือน c

ข้อควรระวัง:

  • --hard ทิ้งการแก้ที่ยังไม่ commit ด้วย และกู้ไม่ได้
  • ห้าม reset แล้ว push --force บน main ที่ทีมใช้ เพราะคนที่ดึง d, e ไปแล้วจะมีประวัติไม่ตรงกับ GitHub

ตาข่ายนิรภัย: ถ้า reset พลาด ใช้ git reflog ดูรายการตำแหน่งที่ HEAD เคยอยู่ แล้ว git reset --hard <hash> เพื่อกลับ (ใช้ได้กับของที่เคย commit ไว้แล้วเท่านั้น และ Git เก็บ reflog ไว้ตามค่าเริ่มต้นประมาณ 90 วัน ส่วน commit ที่ไม่มี branch ชี้อยู่เก็บประมาณ 30 วัน)

สรุปว่าใช้อะไรเมื่อไหร่

สถานการณ์คำสั่ง
ดูของเก่าเฉยๆgit switch --detach <hash>
ทิ้งการแก้ที่ยังไม่ commitgit restore <ไฟล์>
commit แล้ว push แล้วgit revert <hash>
commit แล้ว ยังไม่ pushgit reset

หมายเหตุ: ตัวอย่างสมมติว่าทีมรวมโค้ดผ่าน PR บน GitHub แบบ Create a merge commit (ค่าเริ่มต้น) ถ้าทีมตั้งเป็น Squash and merge ภาพของ main จะต่างจากที่วาดไว้
